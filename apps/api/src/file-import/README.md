# 거래 내역 파일 가져오기 (`src/file-import`, W10 위챗페이 · W11 알리페이)

위챗페이·알리페이 "개인 대조용(用于个人对账)" 거래 내역 파일(위챗 xlsx·예전 CSV, 알리페이 CSV)을 **브라우저에서만** 읽고, 사용자가 고른 결제만 지갑에 저장한다(`Transaction.source = FILE_IMPORT`). 파서는 공급자별 모듈(`apps/web/src/features/file-import/parsers/<provider>.ts`)이고 서버 계약은 공급자와 무관하게 같다. 공급자를 더할 때: `FILE_IMPORT_PROVIDER_VALUES`(shared) · Prisma enum `file_import_provider`(값 추가 마이그레이션) · `providers.ts`(통화) · 웹 `PROVIDERS`·`PARSERS`.
별도 동의는 받지 않는다(직접 입력과 같은 성격 — 처리방침에 수집 항목·방법 반영).

## 흐름

```
화면(브라우저)                                   서버(file-import)
파일 선택 → 파싱·필터(支出 + 가맹점 결제 + 성공)   — 파일·원문 행은 서버로 가지 않는다
txnDigest = SHA-256("{provider}:{거래 번호}")   — 위챗 交易单号 · 알리페이 交易订单号. 결과에 보이는 결제 행만
                                                 (필터로 뺀 송금·홍바오·이체·충전·중성·환불 행은 다이제스트도 만들지 않는다)
POST /api/wallet/entries/file-import/check ──▶ 대조값 배열만 → 본인 importKey와 대조("추가됨"). 저장·로그 없음
GET  /api/fx/spot-series?base=&from=&to=   ──▶ 기간 고시(결제 시각 기준 "약 ₩"은 화면이 계산 — 시각은 보내지 않는다)
(자동 연결될 여정·여정 이름은 화면이 내 여정 목록으로 정한다)
POST /api/wallet/entries/file-import       ──▶ 검사(S7 규칙) → 한 트랜잭션으로 지갑 저장 + 여정 자동 연결, 이미 있으면 건너뜀
```

## API 계약

| 메서드·경로 | 요청 | 응답 | 에러 |
|---|---|---|---|
| `POST /api/wallet/entries/file-import` | `{ provider: 'WECHAT' \| 'ALIPAY', items: [{ txnDigest, occurredAt, amount, currency: 'CNY', merchantName }] }`(1~200) | 201 `{ items[{created, entryId}], created, skipped, linked }`(요청 순서) | 400 `VALIDATION_FAILED`(모르는 공급자 포함), 404(꺼짐 · 켜지지 않은 공급자), 429 `FILE_IMPORT_RATE_LIMITED`·`FILE_IMPORT_DAILY_LIMIT`(`details{retryAfter, retryAfterSec}` + `Retry-After`)·`RATE_LIMITED`(IP), 503 `FX_RATE_UNAVAILABLE` |
| `POST /api/wallet/entries/file-import/check` | `{ provider, txnDigests: string[] }`(1~500, **대조값만** — 일시·금액·가맹점은 400) | 200 `{ imported: boolean[] }`(요청 순서) | 400, 404(꺼짐 · 켜지지 않은 공급자), 429 |
| `GET /api/fx/spot-series?base=&from=&to=` | KST 날짜, 최대 400일 | 200 `{ currency, rates[{rate, effectiveAt}] }`(기간 안 고시 + 직전 1건, 오름차순) | 400 |

- 타입: `@yeojeong/shared` `api/file-import.ts`. 계약 밖 필드(상품·결제 수단·가맹점 주문 번호·비고·거래 번호 원문·clientRequestId 등)는 400(전역 ValidationPipe `forbidNonWhitelisted`). 검증 오류는 값을 되돌리지 않는다.
- `txnDigest`: 소문자 hex 64자. `occurredAt`: 오프셋이 있는 ISO 8601만(없으면 400 — 서버 시간대로 읽히지 않게).
- **한 트랜잭션**: 사용자 advisory lock(`file-import:{userId}`) → 이미 있는 거래 확인 → 일일 상한 → 여정 id 순으로 여정마다 한 번만 잠그고 그 여정 건을 몰아서 저장. 원화 1억 상한(지갑에만 넣는 건은 결제 시점 매매기준율 추정)·환율 없음·일일 상한 중 하나라도 걸리면 아무것도 남지 않는다(검사 오류 경로는 `items.N.*`). 제한 시간 60초.
- 검사(하나라도 걸리면 아무것도 저장하지 않는다): 시각 범위(미래 불가·365일 이내 — `occurredAtError`), 가맹점 정리 뒤 40자(`memoError`), 금액(양수, 소수 2자리 — `manualAmountError`), 원화 1억 상한(저장 때), 공급자 통화(WECHAT·ALIPAY = CNY), 같은 요청 안 중복 `txnDigest`(`items.N.txnDigest` `duplicate`).
- 같은 거래(사용자 + 공급자 + txnDigest)는 한 번만 저장한다: 이미 있으면 `created=false`(skipped). 동시에 같은 건을 저장하면 부분 유니크 `transactions_file_import_ref_key`가 막고 먼저 들어간 항목을 돌려준다. 그래서 다시 보내도 안전하다(요청 단위 clientRequestId는 두지 않는다).
- 여정 연결은 직접 입력과 같다: 결제 시각이 기간 안인 예정·진행 중 여정에 미확정(PENDING)으로. `check`의 `inTripId`가 같은 규칙의 미리 보기다. 저장한 항목은 지갑에서 직접 입력처럼 고치고 지운다.
- 호출 제한: 저장은 **사용자 ID 기준 1분 5회**(`FileImportRateGuard`, 전역 Throttler 저장소 — 인스턴스 메모리, 검증에 걸리는 요청도 센다 → 429 `FILE_IMPORT_RATE_LIMITED`) + IP 기준 1분 60회. 확인은 IP 기준 1분 30회. **사용자당 KST 하루 새 저장 2,000건**(`FILE_IMPORT_DAILY_MAX`, 이미 있던 거래는 세지 않는다 → 429 `FILE_IMPORT_DAILY_LIMIT`, `retryAfter` = 다음 KST 자정). 화면은 200건·500건 넘으면 나눠 보낸다(요청 본문 100kb).
- 확인(check)은 대조만 한다: 요청한 회원 본인의 FILE_IMPORT 항목과만 비교하고(importKey에 사용자 ID — 다른 회원이 같은 거래를 저장해도 답이 달라지지 않는다) 저장·접근 기록·로그를 남기지 않는다.

## 저장하는 것 · 하지 않는 것

| 값 | 처리 |
|---|---|
| 결제 시각·금액(부분 환불은 순액)·통화(CNY)·가맹점(交易对方 — 가맹점 결제 행만, 40자) | 지갑 항목(`transactions`)에 저장 |
| 공급자 | `transactions.import_provider`(enum `file_import_provider`: WECHAT · ALIPAY — `20261030090000_file_import_alipay`). FILE_IMPORT 행에만 있다(CHECK `transactions_import_provider_check`) |
| `importKey` | `externalRef` = HMAC-SHA256(**`IMPORT_KEY_HMAC_KEY`**, `file-import:v1\|{provider}\|{userId}\|{txnDigest}`) hex. 사용자마다 다르다 |
| 거래 번호(위챗 交易单号 · 알리페이 交易订单号) 원문 | 서버로 오지 않는다(브라우저가 SHA-256 다이제스트만 보낸다) |
| `txnDigest` | DB·로그·응답 어디에도 없다. HMAC 재료로만 쓰고 버린다(로그 마스킹 키 `txnDigest`·`txnNo`·`txnNos`) |
| 위챗 商品·支付方式·商户单号·备注·收/支·当前状态 · 알리페이 对方账号·商品说明·收/付款方式·商家订单号·备注·交易分类·收/支·交易状态 · 파일 자체 | 서버로 오지 않는다(받으면 400). 알리페이 对方账号·收/付款方式·商家订单号·备注는 브라우저 정규화(pick) 단계에서도 접근하지 않는다(아래 알리페이 절) |
| 접근 기록 | 저장만 `IMPORT_FILE_ENTRIES` — `details = { provider, requested, created, linked, outcome: OK\|FAILED }`(금액·가맹점·거래 번호 없음, 실패해도 실제 만든 건수 0으로 남긴다). 확인(check)은 남기지 않는다 |

- `IMPORT_KEY_HMAC_KEY`는 카드 불러오기와 같은 전용 키다. **교체 금지**(바꾸면 "추가됨" 판정이 끊기고 같은 거래를 다시 저장할 수 있다). 재료 형식(`file-import:v1|…`)도 바꾸지 않는다.

## 잠금 순서

- 일괄 저장은 사용자 advisory lock → 여정 id 오름차순(Trip FOR SHARE → expenses advisory). 지갑 항목 여정 바꾸기(현재 → 대상)도 트랜잭션 처음에 두 여정을 같은 오름차순으로 잡는다(`lockTripsInOrder`) — 서로 교착하지 않는다.
- 그래도 교착(40P01·P2034)으로 끊기면 409 `CONFLICT`(다시 시도하면 된다).

## 알려진 한계(그대로 둔다)

- 사용자 ID 기준 호출 제한은 전역 Throttler 저장소(인스턴스 메모리)를 쓴다. Cloud Run 인스턴스가 여럿이면 인스턴스마다 센다(전체로는 최대 인스턴스 수 × 5회/분). 하루 2,000건 상한은 DB 기준이라 인스턴스와 무관하다.
- 파일 파싱은 주 스레드에서 한다(Worker에는 `DOMParser`가 없다). 파일 5MB·항목 압축 2MB·데이터 2만 행·칸 1,000자 상한으로 멈춤 시간을 묶었다.
- (재검증 C) 일괄 저장은 최대 200건을 한 트랜잭션으로 넣는 동안 대상 여정의 expenses advisory lock을 배타적으로 들고 있어, 그동안 동행자의 그 여정 결제 변경이 잠시 기다린다. 사용자당 1분 5회라 남용 폭은 작다. 길어지면 묶음 크기(FILE_IMPORT_ITEMS_MAX)를 줄인다.
- (재검증 D) 화면의 직접 입력 글자 수 세기는 `\p{Cf}`를 지우지 않아 서버(`cleanMemo`)보다 많이 셀 수 있다. 화면이 더 엄격할 뿐 서버 거절은 생기지 않는다.

## 시각 규칙

- 위챗·알리페이 파일의 `交易时间`("2026-10-01 12:34:56")은 **중국 표준시(UTC+8, 서머타임 없음)** 로 본다. 화면이 `+08:00`을 붙여 보낸다("2026-10-01T12:34:56+08:00").
- 서버는 그 순간(instant)을 그대로 저장하고, 지갑·여정은 KST로 보여 준다 → 한국 시각은 **1시간 뒤**(13:34:56 KST). 날짜 경계: 중국 23:00~23:59 결제는 KST로 다음 날 00시대다.

## 화면 파서(`apps/web/src/features/file-import/parsers`)

- 읽기: 5MB·데이터 2만 행·칸 1,000자·CSV 한 행 200칸(넘으면 format) 상한. zip 머리면 xlsx(첫 시트, `fflate` 압축 해제 + 브라우저 `DOMParser` — 항목 20MB·합계 40MB 선언 크기 상한, 1MB 넘게 풀리는 항목은 압축 비율 100배 초과 거절, 항목 압축 크기 2MB 상한(해제 CPU 시간), 압축본이 선언 크기보다 1KB 넘게 큰 항목·실제 풀린 양이 선언과 다른 항목 거절, DOCTYPE·ENTITY 거절). Web Worker로 옮기지 않은 이유: Worker에는 `DOMParser`가 없어 XML 파서 의존성을 더해야 한다 — 크기·비율·행 상한으로 주 스레드 정지 시간을 묶었다, xlsx가 아닌 zip·OLE(암호 Excel)는 "압축을 풀고 올려 주세요"(HF-66c), 그 밖은 CSV(UTF-8 BOM · UTF-8 · GB18030 자동 감지). 요약·안내 블록 줄 수는 세지 않고 헤더 행(위챗: 첫 칸이 `交易时间`, 알리페이: `交易时间`·`收/支`가 있는 행)을 찾아 열을 이름으로 고른다. 파서 묶음은 파일을 고를 때 지연 로딩한다.
### 위챗페이(`parsers/wechat.ts`)

- 가져오는 것: `收/支 = 支出` + 가맹점 결제 유형(`商户消费`·`扫二维码付款`·`二维码付款`·`付款码支付`) + 성공(`支付成功` 등). 전액 환불(`已全额退款`)은 "환불됨"으로 보이고 고를 수 없다. 부분 환불(`已退款(￥x)`·`部分退款`)은 순액, 환불액을 못 읽으면 원 금액 + "부분 환불".
- 빼는 것: 홍바오·이체·群收款 등 사람 사이 거래(결과 화면 "송금·홍바오 N건은 제외했어요"), 충전·출금·중성(`/`)·그 밖의 수입·실패·모르는 유형·1년 넘은 결제(조용히).
- 가맹점 이름: 제어문자 → 공백, 보이지 않는 서식 문자(`\p{Cf}` — 양방향 제어·폭 없는 공백, ZWJ 제외) 제거, 40자. 서버 `cleanMemo`도 같은 규칙(직접 입력 메모 포함), 화면은 `<bdi>`로 격리한다.
  카드 불러오기 importKey 재료(승인번호 없는 줄의 가맹점)는 **옛 정리 규칙으로 고정**(`cleanMemoForImportKeyV1` · `merchantKeyMaterialV1`) — 이미 저장한 CARD_IMPORT 키가 바뀌지 않는다(테스트로 고정).
- 읽지 않는 열: `支付方式`·`商户单号`·`备注`. `商品`은 `交易对方`이 비었을 때 가맹점 이름 대신으로만 쓴다. 거래 번호는 파싱하면서 바로 다이제스트로 바꾸고 원문은 화면 메모리에도 남기지 않는다.

### 알리페이(`parsers/alipay.ts`, W11)

- 파일: 我的 → 账单 → ⋯ → 开具交易流水证明 → 用于个人对账(최대 1년) → 이메일 zip(암호 — 비밀번호는 앱 开具记录). 풀면 CSV(대개 GBK, UTF-8 BOM도 읽는다). zip을 그대로 올리면 "압축을 풀고 올려 주세요"(HF-66ac). Excel로 다시 저장한 xlsx도 읽는다.
- 헤더: `交易时间,交易分类,交易对方,对方账号,商品说明,收/支,金额,收/付款方式,交易状态,交易订单号,商家订单号,备注`(값 끝 탭·줄 끝 쉼표). 위쪽 안내문(약 24줄)은 세지 않고 `交易时间`과 `收/支`가 함께 있는 첫 행을 헤더로 본다. 아래 합계·안내·구분선은 시각 칸이 날짜가 아니라 건너뛴다. `交易分类`·`商品说明`이 없는 형식도 읽는다(`交易号`·`商品名称`·`金额（元）` 별칭).
- **버리는 열**: `对方账号`(상대 계정) · `收/付款方式` · `商家订单号` · `备注`. CSV를 쪼개는 단계(`parseCsv`)에서는 모든 칸이 파서 지역 변수(행 배열)에 잠시 올라가지만, 정규화(`pick`) 단계에서 이 열은 위치도 찾지 않고 칸에 접근하지 않으며 저장·전송·보관하지 않는다(결과 타입에 자리가 없고 행 배열은 파싱이 끝나면 버린다). 테스트: 데이터 행의 칸 접근을 기록해 정규화 단계가 이 열을 한 번도 읽지 않음을 확인. `交易对方`은 가맹점 결제로 남는 행에서만 가맹점 이름(비면 `商品说明`, 둘 다 비면 "알리페이 결제").
- 가져오는 것: `收/支 = 支出` + 가맹점 결제(아래 제외 목록에 걸리지 않음) + 성공(`交易成功`·`支付成功`·`付款成功`·`已支付`·`交易完成`·`已完成`).
- 송금·이체(결과 화면 "송금·이체 N건은 제외했어요"): `交易分类` `转账红包`·`亲友代付`, 또는 `商品说明`이 `转账`·`红包`·`发红包`·`收红包`·`亲情卡`·`亲友代付`로 시작(방향 무관 — 받은 红包도 센다).
- 조용히 빼는 것: 분류 `投资理财`·`信用借还`·`充值缴费`·`账户存取`·`退款`·`收入`·`理财`·`还款`, 상대 `余额宝`·`余利宝`·`花呗`·`借呗`·`蚂蚁财富`·`蚂蚁消费金融`·`网商银行`·`基金`, 商品说明 `提现`·`充值`·`还款`·`余额宝`·`余利宝`·`理财`·`基金`·`转入`·`转出`, 支出가 아닌 행(收入·不计收支), 실패·대기(`等待付款` 등)·0원·날짜 오류. 목록은 공개 자료로 추정한 값이라 `alipay.ts` 위쪽 상수에 모아 두었다(실파일로 조정).
- 환불(화면 규칙은 위챗과 같다 — 전액 "환불됨" 비활성, 부분 순액 + "부분 환불 −CN¥x"): 알리페이는 환불을 **별도 행**으로 낸다(支出이 아니고 `交易状态`에 `退款` · `交易分类 = 退款` · `商品说明`이 `退款`으로 시작).
  - 짝짓기: 환불 행 `交易订单号`가 원 결제 `交易订单号`와 **같거나**, `_`·`*` 앞부분이 같으면 그 결제의 환불. 한 결제에 여러 환불이면 합친다. 합계 ≥ 원 금액 → 전액, 작으면 부분(순액).
  - 원 결제가 `交易关闭`: 짝지은 환불이 있으면 전액 환불, 없으면(결제 전에 닫힌 주문) 뺀다.
  - 원 결제 행 상태가 `退款…`: 짝지은 부분 환불이 있으면 순액, 없으면 전액 환불.
  - 짝을 못 찾은 환불 행(원 결제가 파일 기간 밖)은 조용히 뺀다. 같은 번호의 결제가 두 번 있으면 처음 것만.
